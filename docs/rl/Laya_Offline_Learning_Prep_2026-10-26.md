# Laya offline learning preparation — 26 October 2026

Prepared on 26 October 2026 (IST); exact artifact verification time is recorded in `sample-v0/validation.json`. Scope: discovery, derived sample and design. Training, deployment and policy adoption remain later work. Raw archives, frozen cohorts and active C39 were preserved. Nothing was pushed or committed from this diagnosis.

## Executive decision

Start with a qualified **operations decision dataset**, retaining English Laya and `laya-typed-decisions` as controls. The broader [System One review](laya_helper_runs/training-discovery-20261026/system-one-shortlist.md) adds Jiwo v2 for quality, Vela for a tiny complete-menu scorer, and d1-600M for its documented Vulkan route; Kev is the alternative continuation-training starting point. No candidate is adopted or demonstrated better in Factorio. Train the model to select a useful offered operation from its observed state, with calibrated uncertainty. Deterministic tools continue to own geometry, validation and execution. Preserve the full decision distribution during training; the externally validated response remains the selected offered ID and confidence.

Use the historical data first for supervised warm start and measured outcome prediction. Advance to conservative policy improvement only after checking the critic's support and attribution. Collect fresh, disposable on-policy trajectories for environment-reward RL later. The current RLCD trainer uses rewards derived from supplied answer distributions; feeding it historical choices does not turn those choices into game-reward RL.

The user directs the next several cohorts toward model and fine-tuned-checkpoint comparisons. The [cohort sequence](Laya_Model_Checkpoint_Cohort_Plan_2026-10-26.md) separates released-model screening, within-backbone fine-tuning gains, checkpoint progression and independent confirmation. First qualify actual learned decision authority: the inspected clean ops launcher currently offers guided/uniform policies, so merely recording a model name would not expose the model treatment. No campaigns or training are launched by this plan.

Keep useful decisions from failed runs. A passing run is a trajectory label, not a certificate for every action. A construction wait, partial prerequisite or temporary batch can be useful despite `ok=false`. A tool or planner bug should teach a diagnostic model about that failure, while its affected window is withheld from strategic preference labels. No same-seed cross-arm outcome creates a chosen/rejected action pair at an identical state.

## What was measured

The [corpus audit](laya_helper_runs/training-discovery-20261026/corpus-audit.md) indexed **1,958,231 decision newlines in 13,478 unique paths**, with 2,814,264,303 stored payload bytes across the two local host namespaces. These are inventory figures. Identical-file hash deduplication leaves 9,310 hashes / 1,593,080 newlines; record-level independence remains uncounted. The audit sampled 11,657 records from 447 files, found no malformed JSON, and matched every sampled source hash. Its sample favors early records and does not estimate population rates.

The first full metadata scope is **C35–C38: 480 planned jobs = 479 completed + one prepare failure**, reporting **115,413 decisions**. Each planned manifest matches its status registry. The source manifest retains every job, including the C38 prepare failure. C39 is excluded throughout this discovery.

The derived [sample manifest](../../data/laya-training-prep/20261026/sample-v0/manifest.json) records **4,664 inspected decisions from 16 deliberately selected trajectories**, yielding **192 first/middle/last-window examples**. The selection is the first C6-ever passer and first non-passer in each arm; C38 has no passers, so its first and last completed jobs were selected. This oversamples some passing trajectories and is unsuitable for population-rate estimates.

Seven selected files were recovered from the compressed indexed corpus and their complete uncompressed hashes/byte counts matched the audit. Nine selected whole-world files were hashed at preparation time; no prior indexed hash was available for those nine. Record counts matched job-reported decisions in all 16; run IDs, consecutive indices, monotonic ticks, offered choices, menu/distribution correspondence, finite positive propensities and probability sums were checked throughout those files. Frozen action/predicate files were matched to the recorded source hashes or clean recorded git revision. This verifies provenance and syntax, not semantic label correctness.

The selected trajectories contain **292/4,664 menus with more than 20 options (largest 29)**. This is a concrete compatibility issue: the current Laya inference contract supports at most 20 options. In the 192 emitted rows, all 13 oversized menus are in S1; exclusion can remove later science choices. Preserve complete historical menus and flag these rows. Before fitting, either qualify a larger-menu model/adapter or report their exclusion; silently truncating menus changes the decision problem and can remove the selected action. The smaller-menu subset's phase/outcome bias must be reported.

All four cohorts share **one identical source-save SHA-256**. The sample has no train/calibration/test assignment. It cannot provide a strict unseen-map split. Three checkpoint-predicate file hashes occur across these cohorts: C35 differs from C36/C37, and C38 differs again. Exact hashes identify contracts; their semantic compatibility still needs a reviewed diff. C38 also changed the stop contract to a decision-or-idle rule and ended before exposure to clearance. Keep its observed local operation results as diagnostics; exclude its trajectory failure from normal mission-return fitting.

## Data organization

Keep four linked tables in the eventual release. This discovery sample combines them in each JSONL row for convenient inspection; separate tables avoid repeating large terminal payloads in the full export.

1. **Sources and episodes:** host namespace, cohort, every planned job/status, source-save and ancestor lineage, policy seed, arm, full revision and frozen diff, engine/mod/tool hashes, predicate identities, windows, stop cause, observation coverage and resume/import ancestry.
2. **Decisions:** exact pre-choice state, phase, exact ordered offered options/parameters/features and objective. Preserve input/render/tool versions. In a model-specific projection retain stock versus reservations, ownership versus item stock, transaction status, shortages, observed rates/windows, progress since last attempt, and option costs. Unknown facts remain unknown. Tokenization must preserve all offered IDs and distinguishing facts.
3. **Observed outcomes:** logged chosen ID, behavior authority and probability/distribution; typed receipt, transaction ID and verified delivery/progress facts; next decision observation with tick/duration and boundary evidence; any terminal labels, measured returns and confidence in attribution. Unchosen options have no outcome label.
4. **Quality and splits:** source integrity, lineage/contract coverage, syntax/representability, censoring, fault and duplicate/retry reason codes, task-specific eligibility and weights. Preserve excluded rows in the ledger. Different tasks can use different masks.

The [discovery schema](../../data/laya-training-prep/20261026/discovery-row.schema.json) separates `input`, `behavior`, `labels`, `quality`, `lineage` and `provenance`. `labels.next_decision` is a delayed observation, rather than a claimed immediate after-state. Reward and absorbing-terminal fields are null. Every row has `train_ready=false`, and the schema enforces that restriction. This is a reviewable format, not input accepted by the existing fine-tuner.

Do not put current-choice outcomes, terminal success, source arm/cohort identity, future stock or next-state observations in model input. Historical outcomes already present in the recorded pre-choice state are legitimate context. Keep behavior probabilities and rule weights for propensity/support auditing; treating them as targets would chiefly reproduce the guided sampler. A prospective value-model dataset uses the chosen action as a conditioning input and only that action's observed outcome as its label.

## Cleaning and compatibility rules

Preserve the immutable corpus and generate new content-addressed shards and a completed manifest. Refuse overwrite, path/hash conflicts or incomplete exports. The discovery script only reads raw evidence and writes a new output directory. It is bounded and loads one selected trajectory at a time; the production adapter should stream all rows.

- Resolve a registered world directly when available; otherwise join its exact namespace/path through CONDENSED/index records. Verify stored payload size, decompressed bytes and SHA-256. Reconcile identical hashes across hosts, archive copies, resumes and imports; preserve all provenance aliases.
- Account for all planned statuses before selecting examples. Unstarted/prepare-failed jobs have no decision example, but remain in the release denominator. Interrupted observed prefixes may be eligible for local receipt labels with censoring; their missing future is unknown.
- Key decisions by immutable run identity + decision index, with the raw-record hash. Duplicate identities with different content require quarantine. Identical files are storage duplicates, not independent evidence. Preserve sequential retries and their timing in the canonical data.
- Partition by action, predicate, renderer and measurement/stop contracts. A file hash change triggers semantic review. Pool only proven-compatible objectives; bind legacy outcomes to their original definition. Today's C5 definition cannot retroactively label an old plastic-stock endpoint.
- Treat unknown observations as null. A missing milestone list, unsupported query, `planned` result or `construction_pending` status never becomes a success. A completed process can still be a censored/failed mission. Strict ever, strict fresh-final, rate proxy and Laya C6-v2 remain separate labels.
- Train outcome classes on observed lifecycle facts (submitted, constructing, prerequisite advanced, batch active, output delivered, producer ready, refused, fault, unknown). Collapse classes only through an explicit versioned mapping. `ok` alone is a receipt field.
- Quarantine tool/environment/validator/planner faults from strategic preference credit, retaining fault labels for diagnosis. Intended material difficulty remains an observed outcome; prefer avoiding an unchanged retry only when relevant facts establish the retry was unchanged and an independent alternative is supported.
- Cap the aggregate training weight of repeated unchanged context/action/outcome within a trajectory, retaining multiplicity. A reasonable first ablation gives such a group total weight one. Changed stock, allocations, transaction state, rate window or retry horizon breaks the group. Preserve waits/reconciliation with measured progress. Exact-byte dedup alone misses loops whose history/timestamps change.
- Balance by trajectory and milestone stratum after a natural-prevalence evaluation set is reserved. Report effective sample size, per-phase/action coverage, failure classes, menu sizes and weight lost to each mask. Oversampling rare C6 outcomes changes prevalence and needs calibrated weights.

For C1/C5/C6 and science endpoints, record predicate code identities and actual observation coverage before assigning labels. In C37, consumer-cell ownership/retention is a promising decision feature; old post-run ownership cannot be inserted into earlier inputs. Derive it only where the pre-choice snapshot actually provides it, otherwise mark unknown and improve future collection. A model cannot learn to select an operation absent from its offered menu.

## Learning stages and targets

**Stage A — qualified supervised warm start.** Fit a typed policy using local expert/replay labels when supported, and separately evaluate behavior-cloning of qualified historical choices. The latter is a compatibility baseline, not improvement evidence. Qualified successful local progress can be weighted, with an explicit selection-bias ablation; avoid all-pass/all-fail episode relabeling. Preserve uncertainty when several choices are defensible. Use existing guided and uniform samplers, untouched English Laya, typed sibling and a small feature-based ranker/critic as baselines. The feature model establishes whether language capacity adds value to these mostly structured facts.

**Stage B — learn from observed failures and delayed success.** Fit a separate action-conditional outcome model on logged actions, with fault/censor masks and predicted delivery/progress at a specified game-time horizon. Fit a milestone value model only after a version-compatible trajectory join. Train policy preferences from an independently validated critic only inside supported state/action regions, with a behavior/KL constraint and uncertainty rejection. An outcome classifier's prediction for an untried option is an estimate, never a measured counterfactual label. Test calibration, support and overestimation before allowing it to guide a policy.

**Stage C — conservative offline RL, conditional on usable transitions.** Require ordered `(observation, menu, action, reward, next observation, next menu, duration, terminal, truncation)` with verified run/resume boundaries, objective versions and behavior policy. Operations are variable-duration decisions, so discount over elapsed game time, for example `gamma^(delta_ticks / reference_ticks)`. Preserve truncated bootstrap targets instead of treating a time cap as absorbing failure. IQL/AWAC-style advantage weighting is a candidate experiment after these gates, rather than the starting assumption. Logged propensities permit support checks and exploratory clipped/weighted estimates; long-horizon importance ratios and hidden wrapper decisions make such estimates insufficient for promotion.

**Stage D — fresh on-policy RL on disposable worlds.** Roll out a frozen admitted warm start, keep exploration, score the actual executed chosen operation and measured trajectory, and update with clipped policy/advantage objectives on the typed offered-action distribution. A KL reference and bounded compute/action budget limit drift. Compare matched policies under identical action, predicate, clock and toolkit versions. Train policy strategy while improving missing shared facts/operations independently; a mechanical tool repair is a separate factor.

Suggested reward specification to freeze before training: terminal mission completion is the primary objective; strict C6-ever/fresh-final and earlier milestones are explicitly named curriculum objectives until science is exposed. Use verified first achievement or potential-difference shaping to avoid reward from toggling milestones, plus measured elapsed game time/resource cost. Sustained-service rewards need actual consumption/delivery windows. Idle/retry penalties apply only to verified unproductive repetition; productive waits and environment faults require separate treatment. Stock alone must not reward indefinite hoarding, and a timeout cannot outrank mission completion because it is cheap. No reward constants were fitted or invented for the sample.

The strongest later preference data comes from **fresh matched-state continuations**: freeze one disposable snapshot, offered menu, objective, clock/measurement contract and replay seed set, execute alternatives, and compare verified downstream completion/service under equal budgets. Replicate noisy outcomes. Keep all-failed alternatives unresolved. The separate historical counterfactual archive is a candidate source, but was not audited here; previous docs reporting usable labels do not certify its current retained files. Do not mix its lab geometry profile into ops training without an explicit compatible task adapter.

## Splits and evaluation

For strict generalization, group identical source saves and known common map/ancestor lineage, with all arms, repeats, resumes, hosts and imports together. The current first scope has one save, so this split is degenerate. Leave it unassigned until choosing an explicit evaluation objective.

A first within-map pilot can group by source-save + policy seed, reserve a calibration partition, use development seeds for model selection, and freeze final seeds before the first fit. Describe the result as policy-seed generalization on one map. Exact trajectory aliases must never cross splits. Shared exact pre-choice inputs can occur across independent seed trajectories: quarantine these inputs from offline novelty metrics instead of treating them as unseen; report that removal. Full episode tests still include natural shared starts. Grouped uncertainty estimates must operate at episode/seed level, not treat thousands of correlated decisions as independent samples.

Offline checks: complete-menu validity and representability; per-action/phase coverage; qualified-target NLL/Brier and reliability by confidence/coverage; outcome PR/recall by class and phase; calibrated uncertainty on rare/fault/unknown cases; positional shuffling, ID remapping, changed reservation/stock and changed retry-state tests. Calibration uses its own split. Historical chosen-action agreement measures imitation only. Token/renderer audits must show every offered option survives the configured input/head budgets; no weight download was done to measure tokenizer truncation here.

Policy effectiveness requires matched Factorio episodes with a frozen toolkit and predeclared windows. Report **strict C6-ever primary, strict fresh-final C6 secondary**, earlier strict C2/C3/C4/C5 service guards, science endpoints when exposed, tool/safety stops, returns/censoring, wall/game time and the full planned denominator. C5-ever, final and sustained plastic consumption are distinct. Compare against guided/uniform behavior plus each model baseline. Use development cohorts for tuning and a fresh untouched final test; historical cohorts repeatedly used for diagnosis are development data. Add unseen-map families before claiming map generalization. Follow the repository adoption rule; offline scores grant no default deployment.

## Model choice as of 26 October 2026

The [primary-source review](laya_helper_runs/training-discovery-20261026/model-review.md) inspected the publisher's public model list, pinned model cards/configs/licenses and upstream training documentation. It found three public Laya checkpoints and no newer public Laya checkpoint in that list. Model timestamps alone do not establish better decisions.

**Expanded discovery:** the [System One shortlist](laya_helper_runs/training-discovery-20261026/system-one-shortlist.md), [small-model audit](laya_helper_runs/training-discovery-20261026/system-one-small-review.md) and [encoder audit](laya_helper_runs/training-discovery-20261026/system-one-encoder-review.md) supersede the earlier narrow challenger order below. Prioritize Jiwo-0.8B v2 and Vela-2.0-0.3B alongside the Laya controls; assess d1-600M for Miniship Vulkan and Kev for public fine-tuning support. Native menu support is 255 for Jiwo/Vela/Kev and 62 for Intern, whereas Julia's 20 and WaterSheep's 10 require an explicitly changed menu procedure. Hardware identification confirms Miniship's Radeon 680M/3 GiB firmware VRAM and about 28 GiB RAM; runtime fit/latency remain unmeasured. The previously discussed generic generative models are lower priority than these trained decision scorers.

For the later **fine-tuning pilot**, the [training-source follow-up](laya_helper_runs/training-discovery-20261026/system-one-finetune-review.md) recommends Laya as control and **Kev-0.8B as the first new model to train**, conditional on a complete-menu context and hardware preflight. Kev has released LoRA/head continuation and keyed soft-target CE; disable generic menu insert/remove augmentation for the operation task and account for context-filtered rows. Vela is the compact custom-trainer candidate. Jiwo's stronger general benchmark evidence does not supply a released trainer or establish greater fine-tuning gains. No candidate's 8 GiB training fit is certified.

- **English Laya (~421M): first baseline.** Closest match to current encoder/typed-head training path, Apache-2.0 declarations, pinned revision `7b928d828b7b0e022f929d9bd2e44165aa270148`.
- **Laya typed-decisions (~421M): first challenger.** Same head family, domain-specialized sibling, pinned `e929ae5cf69bc34259cd2f95c9e91145b818b1f0`. Higher publisher benchmark accuracy across four workflows comes with worse reported calibration; it is not a Factorio result. Strict checkpoint/sequence/LoRA/profile compatibility still needs validation.
- **Qwen3.5-0.8B: deferred generative challenger.** Apache-2.0, pinned `2fc06364715b967f1860aea9cf38778875588b17`. It predates Laya's September repository creation and is not a newer Laya. Requires a separate trainer, bounded constrained offered-ID output and calibrated choice scoring. Its config is multimodal conditional generation; text-only loading and exact memory need validation.
- **FunctionGemma-270M, LFM2.5-1.2B and SmolLM3-3B:** documented alternatives. FunctionGemma has gated Gemma terms/config access; LFM has a conditional license and new architecture/trainer; SmolLM3 is older/larger. No common Factorio benchmark justifies their added integration now. Multilingual Laya uses a different encoder; the corpus's English task provides no initial reason to prioritize it.

Upstream Laya tooling at the pinned source commit advertises version 0.4.16 and supervised soft-CE/RLCD choices. A tooling release is separate from a new checkpoint. Review against this project's custom strict loader, trainable head and supervision before any upgrade.
