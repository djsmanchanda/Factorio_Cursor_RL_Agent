# Laya cohort operations dashboard

This is a separate loopback-only dashboard. It reads disposable cohort evidence; it does not modify campaign files, server saves, server mods, or running Factorio worlds. The explicit client-mod sync button updates only Starship's GUI mod directory. Read `docs/system_invariants.md` before any deployment. The interface covers host admission, registry outcomes, selected-run timings and persistent reviews. Evidence gaps remain explicit below.

## Interface layout

Four tabs (keyboard arrows move between them; the choice, chart range, panel selection, family, milestone and registry state persist in `localStorage`; reviews drafts persist in `sessionStorage`; the snapshot token is never stored):

- **Overview.** A verdict line and four gauges answer "what limits more concurrent runs?": run ceiling vs UPS vs temperature, plus memory, mode and runner instability. Each gauge compares the latest sample with its recorded floor/growth threshold and is labelled Limiting, Past limit, OK or No data (icon plus text, not colour alone). These flags show proximity to a threshold, not proven cause; the scheduler's own recorded reason and `observed_constraints` are shown beside them. The ceiling counts concurrent **runs**, is an upper bound, and safeguards can admit fewer. p95/p98 are slow-tail coverage floors (the 5th/2nd percentile of per-run UPS), explained in the `?` help. Controls sit beside the gauges: stepper plus permanent/temporary ceiling with a live plain-language preview and client-side validation, resume, the editable UPS floors and temperature target (with "now" values and discard), and the one-hour Miniship cooling button with its countdown. Edits are not overwritten by the 30 s refresh. Below: running/queued cohorts, newest first, with a stacked progress bar. Historical queued statuses alone do not establish an active campaign: queued-only cards require current queue or scheduler evidence; all registry records remain on Jobs.
- **Performance.** 6 hours / 1 day / 7 days; stacked panels for runs & caps, slow-tail UPS, temperature, aggregate UPS and memory with a shared crosshair, one tooltip, keyboard inspection (arrow keys), clickable legends, control-event markers (limit, safeguards, cooling, rejected/failed), a recorded-reason lane and a mode lane. Lines break at missing values and at server-flagged gaps, which are hatched; isolated samples draw as dots. Dashed horizontals are the *current* settings. Reason shares come from the server's `reason_seconds` (gaps shown as their own segment). A "Numbers behind the charts" table gives latest/min/max and how many samples had a value.
- **Jobs.** Running servers grouped by cohort (collapsed when more than five): verified listener, Starship viewing route (enable/renew/stop/copy) and **Sync mods to Starship Factorio**, which now opens a confirmation dialog describing exactly what is replaced and never runs automatically. Every action shows busy, success and error state inline and as a toast. The registry below is the operational job list only, sorted by recency, filterable, paged, lazily rendered, with per-cohort run filters and paging. Each run has an expandable review box (expand button, character count, Ctrl+Enter, draft preserved across refresh and failure), paginated saved reviews (newest first, "load older" follows the server cursor) and an inspector dialog for timing and frozen mod hashes (a table, not a JSON dump).
- **History.** Only the curated feed. Strict and proxy families are separate switches; the milestone list comes from the data. Pending, invalid and no-start rows are unranked: hidden unless "Show unranked rows" is on, then shown without any implied zero. Unknown values are striped, never empty bars. Predicate version, comparison eligibility and tick window are chips on the cohort header when arms agree and on the arm when they differ; arms with differing windows or versions are flagged. Early latched finals read "latched, unknown". There is no cross-cohort trend line.

The Reading rules dialog restates the evidence boundaries. The dashboard follows the OS light/dark preference.

## Start and access

The installed user service is `laya-cohort-dashboard.service`. For a separate read-only instance:

```sh
python3 tools/laya_cohort_dashboard.py --repo-root /home/miniship/Github_Desktop/Factorio_Cursor_RL_Agent
```

It binds `127.0.0.1:9138`, without LAN authentication or remote exposure. Starship has the persistent user unit `laya-cohort-dashboard-tunnel.service`; open `http://127.0.0.1:9138` there. A manual alternative is `ssh -L 9138:127.0.0.1:9138 miniship`. The tunnel is for HTTP only; it cannot forward Factorio UDP. `--registry`, `--host-root`, `--data-root` and `--port` override paths and port. Local notes, audit and cooling state go under ignored `data/laya-cohort-dashboard/`; backups of this directory are the operator's responsibility. The example user unit at `systemd/laya-cohort-dashboard.service.example` requires editing absolute paths; the current Miniship instance is installed with controls enabled, plus the persistent cooling recovery timer.

Controls default to disabled. Even with `--enable-controls`, they remain locked unless a fresh scheduler heartbeat identifies a living process with matching protocol and source hash. This is a compatibility check, not a defense against a malicious local user. Do not enable until the updated scheduler has been reviewed, deployed and restarted. The old controller does not share the lock and a manual target bypasses UPS checks. Check active campaigns and deadlines before deployment/restart; do not edit frozen campaign copies or restart campaigns. Preserve the existing host config. Rollback: cancel cooling, stop the dashboard, restore the prior scheduler source and restart only the host scheduler when authorized; the old manual-target bypass returns.

## Controls

The manual ceiling is an upper bound, not a request to immediately fill slots. It can be temporary or permanent, including zero; existing worlds drain naturally. The automatic search and UPS, thermal, memory, mode and runner-instability caps still apply. Temporary ceilings nest and restore the earlier policy; `resume` clears them. A zero-to-nonzero recovery with queued work can bootstrap one unmeasured slot. Floors refer to the 5th and 2nd percentiles of sampled run UPS, respectively, representing p95/p98 coverage, not the 95th/98th numerical percentiles. Changes use the scheduler CLI and its shared file lock. Other clients must also use that lock and updated scheduler code to avoid lost writes.

Cooling requires the persistent recovery service and timer to be installed, enabled and active before it can start. Copy `systemd/laya-cohort-cool-recovery.service.example` and `systemd/laya-cohort-cool-recovery.timer.example` to `~/.config/systemd/user/` without `.example`, replace all absolute paths in the service, then run `systemctl --user daemon-reload` and `systemctl --user enable --now laya-cohort-cool-recovery.timer`. The service must use this dashboard's exact code, evidence, host and data paths. Check `systemctl --user status laya-cohort-cool-recovery.timer`. A user manager must run after reboot; if no login is guaranteed, user lingering must be enabled separately by an authorized administrator. No root or linger change is performed here.

The timer checks the persistent state every minute and retries failures, including after user-manager restart or reboot. At expiry the helper selects Linux balanced and restores the previous scheduler mode only if its token still owns it. Repeating renews the deadline. Explicit scheduler `mode` commands clear ownership. A failed power-saver request attempts immediate rollback; interrupted applications and failed rollback remain recorded for recovery. This is not a BIOS setting. Before uninstalling, cancel cooling, confirm the state is clear, then `systemctl --user disable --now laya-cohort-cool-recovery.timer` and remove the two installed units when authorized. Keep the script and paths available while recovery is pending.

## Evidence and limitations

- Cohort status and planned counts come from registry `job-status.json`, `freeze.json`, `planned-jobs.json`, and the loop queue. A missing job is unaccounted, not a success or failure. Curated source reports are served from the reviewed source allowlist; arbitrary files are not exposed. Dataset snapshots and historical index are descriptive; no final ranking is inferred from partial cohorts.
- Scheduler history is incrementally indexed in `history.sqlite3`, retaining 30 days. Views select 6 hours, 1 day or 7 days. Large windows preserve original extrema rather than averaging percentile samples. Cached JSON reads are limited to 12 MiB per file. Attribution describes reported reasons, not independent causal inference; intervals over ten minutes are omitted. History includes settling, missing samples, thermal, UPS, mode, memory and instability reasons when reported, but no synthetic reason is invented. A recorded `effective_max` from an older scheduler may not include a manual ceiling.
- Running rows inspect the Factorio PID, process executable and world identity, then associate IPv4 UDP socket inodes with the manifest port. This is a point-in-time local check, not a reachability test; wildcard binds have no asserted endpoint, IPv6 is unknown, and loopback cannot be joined directly from Starship. The interface shows connection actions and a client-mod sync button; raw engine/mod lists are omitted. Exact mod hashes are available in run inspection. GUI engine parity and remote reachability are not established by listener inspection. Never use RCON credentials for viewing.
- Historical charts use only the curated feed `docs/rl/laya_cohort_curated_history.json`, covering 7–28 October, C1–C43, retries and selected named campaigns; C44–C46 are explicitly pending. The registry remains the operational job view and sorts newest cohorts first. Strict checkpoints and rate proxies have separate selectors. Missing versions, ineligible comparisons and historical evidence gaps remain explicit. Read `Laya_Curated_History.md` for source qualifications and corrected early tick windows. Hoverable host datapoints, current guard lines and recent control audit markers are available, along with snapshot JSON export. Selected-run charts show recorded policy, executor and client timings; older records show decision cadence separately when timestamps permit. Missing timing is unknown. Typed outcome and classification maps remain separate from the old failure count.
- Notes are append-only user observations, not training labels or learning truth. The snapshot includes a recent tail; each run has a paginated notes API that scans backward in bounded 2 MiB windows, retaining all older observations. Drafts survive refresh in the page session. The HTTP API has Host, Origin and random-token checks; it assumes a trusted local user and must not be proxied to untrusted networks.
- The scheduler, dashboard and recovery timer are deployed. The scheduler heartbeat/source handshake and Starship HTTP tunnel were verified live; the original host configuration was preserved byte-for-byte. Cooling power changes and automatic recovery have fixture coverage only; no power profile was changed to test this feature. Existing campaign processes, saves and mods were untouched. User lingering was already enabled. Deployment backups live under `data/laya-cohort-dashboard/deployment/`.

## Starship viewing routes

For loopback-bound runs, configure `--viewer-bind 100.99.132.51 --viewer-address 100.92.154.27` on the dashboard. The per-server **Enable Starship viewing for 1h** button creates a UDP relay on the private bind address with an OS-assigned port. Only packets from the configured Starship address are accepted; the first client socket owns the route. The dashboard copies packets to the inspected loopback game port, never RCON. The route expires after an hour or when the run/process identity check fails, and can be explicitly stopped. Renewing extends the hour. All relays close when the dashboard exits. No server rebind, save change, mod deployment or automatic GUI join is performed.

Copy the endpoint into Factorio's multiplayer **Connect to address** on Starship. Use the matching Factorio client and server mods; exact frozen mod hashes appear under **Inspect timing**. A local listener and relay are not proof of network reachability or client parity. Direct IPv6 viewing is unsupported.

## Sync the selected run's mods to Starship

**Sync mods to Starship Factorio** verifies the source against that run's frozen mod hashes and transfers it over SSH to `/home/djsm/.factorio/mods`. The enabled-mod list and mod settings are included. Replaced client files/directories are archived under `~/.local/share/laya-cohort-mod-sync/<sync-id>/previous` on Starship; unrelated installed mods are preserved. The transfer manifest is checked before replacing anything, and failed replacements attempt rollback. Requests are serialized to prevent two runs overwriting the client concurrently. No root is used. The running client is not closed; restart it before joining. No sync was performed merely to test the button.
